# 冻结合同漂移：多智能体流水线里合同被悄然改写的两种模式

> 来源：2026-09-10 P0 常用交互优化 Stage 5 review 实证（docs/DEVLOG.md 同日条目；R-01/R-06/R-08 三个 blocker 的根因同族）。GPT 全量 review 是发现渠道——门禁与 558 个测试全绿都拦不住这两类漂移。

## 模式一：合同误读被测试固化（最危险）

实现者误读冻结合同 → 把误读写成**强断言** → 全套件绿 → 误读获得"已验证"的假权威，后续维护者更不敢改。

实例：
- 设计 §5.10 写「cURL 必须 redacted：Authorization…」，实现者读成"排除 Auth 派生 Header 条目"，并写下 `expect(curl).not.toContain('Authorization')`——错误需求被断言钉死（review 语：「不是断言太弱，而是把错误需求理解写成了强断言」）；
- 设计 §3.1.1/§4.9 要求 409 → 树置 stale，实现者认为"clipboard 操作不改 Collection 数据"而选择不置 stale，并把 `stale=false` 固化进测试。

防线：**测试断言的期望值必须能回溯到合同条款原文**——每个关键断言注释引用 §编号；review 时把"断言与合同原文对读"作为独立步骤（绿≠对）。修复此类缺陷时，断言反转要逐条记录依据（是纠正误读，不是弱化）。

## 模式二：跨包备注转述丢失作用域限定

上游包的对接备注在经 orchestrator/下游转述后，**限定词丢失**，局部事实变成全局规则。

实例：Host 包备注「Cut 409 后 token 永不消费但永远无法再成功（**request/源版本已前移**）→ UI 应引导重新剪切」——限定在源冲突；转述进下游任务书时限定词丢失，下游实现成"**任意** 409 都清 token + 提示重新剪切"，把可恢复的目标版本冲突也判了死刑（违反「409 不消费 token、刷新后可重试」合同）。

防线：跨包备注注入下游任务书前，**对照冻结合同原文核验一遍**；转述时保留（甚至加粗）作用域限定词；下游对收到的"上游结论"如有疑问，以合同原文为准而非转述。

## 共同点

两类漂移都不产生红灯——类型、测试、门禁全绿，只有**外部视角对照合同原文逐条审**才能暴露。多智能体并行流水线里，写与判分离（实现者不自审、独立 review 角色对照冻结文档）不是流程装饰，是这两类缺陷的唯一有效防线。
